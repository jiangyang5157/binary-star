## 1. 方法修正（重要，先说清楚）

我第一版的新数据前瞻分析出现了 **+8.60 ATR / 1 小时** 这种离谱数字，查下来是**我自己的匹配 bug**：

* 原做法按"时间差 ≤3 秒"把 wake 关联到 pulse；
* **但 run 7 连续运行了 3 天**，所以 `01:30` 在同一个 run 里会出现 **3 次（9/19、9/20、9/21）**；
* 于是 wake 被关联到了**另一天**的 pulse，前瞻窗口跨了一个隔夜大行情。

**修正**：改为**文件序数锚定**——每条 WAKE / COOLDOWN BLOCK / GATE SHADOW 都关联到它**紧邻的上一条** `SIGNAL DIAG`（这正是 daemon 实际的因果顺序）。修正后逐条核对了价格序列
（01:30:09 那次：78,109.7 → 80,570，ATR 321，MAE 仅 +0.73 ATR），确认真实。

> 影响范围：上一轮（round 1）的游程与前瞻统计用的是**序数窗口**（`for j in range(i+1, ...)` + run 校验），
> 不受此 bug 影响；受影响的只有我这次临时写的匹配逻辑，已废弃。

**复现脚本**：`scripts/sniper_gate_replay.py`（新增，未改动任何既有文件）

## 6. 新的观察项（不改动，仅记录）

### 6.1 session 层才是当前的瓶颈

* **漏掉最大一段**：01:30:09（trending、单信号 `large_trade`、conf 0.32）触发了 wake，
  AI 返回 **NEUTRAL**；随后 1 小时价格从 78,110 走到 80,570（**+7.65 ATR**，MAE 仅 +0.73 ATR）。
  这是本期最大的一段被 session 层放弃。
* **AI 反向覆盖信号**：XAUT 15:05:54 wake 方向 **BULLISH**（conf 0.76），AI 判 **BEARISH** → 做空，
  价格反向走（按其信号方向 MAE **−1.63 ATR**）→ 审计 SL/亏损。
  新窗口 XAUT 只有 3 次 opinion，就出现了 1 次反向覆盖。
* 对照：BTC 有方向性 opinion 的 10 次 wake **全部与信号同向**，质量很好（MFE +2.63 / MAE +0.03）。
  → 问题不是"系统性反向"，而是**低 conf 的 trending wake 被 NEUTRAL 掉**，以及**XAUT 的个别反向覆盖**。

### 6.2 cooldown 不是主要成本

33 次 `COOLDOWN BLOCK`（BTC 32 / XAUT 1），1h MFE 中位 +0.43 ATR、MAE 中位 −0.27 ATR，
**只有 24% 在 1 小时内摸到 +1 ATR**。最大的几个（01:35 +7.59、01:37 +7.45、01:44 +4.33 ATR）
都紧跟在 01:30/01:39/01:48 那几次已入场之后 —— 属于**同一波行情的重复信号**，不是踏空。

   而它是目前唯一持续度量"同源堆叠"的手段；将来若设计新规则，它是有用的基线。
4. **下一个议题改为 session 层**（建议单独立项）：
   * 为什么 trending 中 conf 0.31~0.5 的单信号 wake 容易得到 NEUTRAL？
     （01:30 那次跑了 +8.60 ATR）
   * XAUT 为什么会在 conf 0.76 的 BULLISH wake 上给出 BEARISH 并做空？
5. **`trigger_threshold: 0.34`（XAUT）值得单独复查**：每天 190 次越阈、中位 conf 0.52，
   全靠 gate 兜底。但这需要单独的阈值标定分析，**本轮不动**。
6. **影子期是否继续**：原计划 14 天只跑了 3.65 天。鉴于 R1 已被否决，
   继续跑影子期的价值只剩"验证 3.65 天这个结论是否稳健"。我的建议是**让它自然继续**
   （零成本），但不必为它刻意延长；有新的 regime 轮换时再复算一次即可。

## 9. 对前几轮数字的更正（重构脚本时发现）

在把分析脚本重构成可复用模块的过程中，发现前几轮工具里**两个真实的错误**。核心结论不受影响，但部分数字要更新。

### 更正 1：`wakes/天` 的分母用错了

前几轮用的是**日志墙钟跨度**（09-05 13:23 → 09-18 02:00 ≈ 12.5 天），
但 daemon 实际只运行了其中一部分。用单调时钟逐 run 统计：

| run | 实际时长 |
|---|---|
| 0 | 20.90 h |
| 1 | 27.98 h |
| 2 | 45.09 h |
| 3 | 10.40 h |
| 4 | 8.44 h |
| 5 | 0.35 h |
| **round-1 合计** | **113.2 h = 4.72 天** |
| 6 | 10.21 h |
| 7 | 73.65 h |
| **全部合计** | **197.0 h = 8.21 天** |

→ round-1 报的 XAUT「1.28 wakes/天」按实际运行时长应为 **≈3.4 wakes/天**。
**比率（×7.4 等）不变**，只是绝对值被低估了约 2.6 倍。
本轮新增窗口同理：应为 **3.49 天**（不是墙钟的 3.65 天）。

### 更正 2：旧引擎的 cooldown 时间线排序错误（较严重）

`analyze_sniper_gate.py`（现 `sniper_gate_core.py`）的 `counterfactual()` 用

```python
timeline.sort(key=lambda x: (x[0], x[1], x[2]))   # x[1] = _tsec(t)
```

而 `_tsec()` 是 `%H:%M:%S` 的秒数，**在午夜回绕**。结果是**任何跨午夜的 run
整条 cooldown 时间线被打乱**——8 个 run 里有 4 个中招（`XAUTUSDT run 0: 590/590 个位置错位`）。

**修正**：改为**文件序数锚定 + 单调时钟**（对时间差取 `% 86400` 展开午夜边界），
实现见 `scripts/sniper_gate_replay.py`。

影响与不影响：

| 受影响（旧数字不可用） | 不受影响 |
|---|---|
| `counterfactual()` 的 k=1/2/3 wake 数 | per-pulse 的 confluence / 方向 / same_dir（按文件顺序迭代，无排序）|
| `sniper_gate_policy_experiments.py` 的 P0~P9 全部数字 | 游程与前瞻统计（一直是序数窗口）|
| | 本轮 R1/R2 的核心结论（基于**真实 wake + 前瞻**，不依赖反事实）|

**修正后的 XAUT 反事实**（全量 8.21 天，`k` = `min_active_non_trend`）：

| k | wakes | wakes/天 | gate 拦截 | 拦截 sd=1 | 拦截 sd=2 |
|---|---|---|---|---|---|
| 1 | 223 | 27.16 | 0 | — | — |
| 2 | 108 | 13.16 | 617 | 617 | 0 |
| 3 | **17** | **2.07** | 1258 | 803 | 455 |

对照 round-1 报告的 277 / 118 / 16 —— **量级与结论一致（降到 2 ≈ ×6），但绝对值要按上表更新**。
k=3 的 17 次与实际记录的 20 次 XAUT wake 也基本吻合，可作为自校验。

> BTC 的反事实**不可用**：`trending` 无法从日志推导，脚本只能把非 squeeze 一律当 ranging，
> 于是 20 次 trending wake 全被误判为"该拦"。**BTC 一律以日志里真实的 28 次 wake 为准。**

### 更正 3（脚本结构）

原 `analyze_sniper_gate.py` 同时承担"库 + 决策逻辑 + 报表"，其中的决策逻辑带有上述 bug。
现拆成三个文件，**把 bug 从结构上消除**：

| 文件 | 职责 |
|---|---|
| `scripts/sniper_gate_core.py` | 纯重建库：解析日志、还原 9 个 detector、SignalMemory/Confluence 复现、配置加载。**不含任何时间线逻辑**，因此不可能再犯排序错误 |
| `scripts/sniper_gate_replay.py` | 引擎：序数锚定 + 单调时钟 + cooldown 反事实 + 前瞻游程 + 报告（可复用，不含轮次特有内容）|
| `scripts/sniper_gate_policies.py` | 策略对比 P0~P9，建立在同一套序数时间线上 |
